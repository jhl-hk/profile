The internet is not one network. It is tens of thousands of independent networks that agree to pass traffic to each other. The protocol that makes this agreement work is **BGP**, the Border Gateway Protocol. This post explains what BGP is, how it decides where traffic goes, and what you need to start using it yourself.

# What is BGP?

BGP is the routing protocol that connects networks to each other. Every ISP, cloud provider, CDN and large company runs it at the edge of its network. When you open a website, BGP is what told your ISP's routers which direction to send your packets.

The current version is **BGP-4**, defined in [RFC 4271](https://www.rfc-editor.org/rfc/rfc4271). It has carried internet routing since the mid-1990s.

BGP does not move your packets. Routers forward packets. BGP is how routers learn *where* to forward them.

# Autonomous Systems

BGP works between **Autonomous Systems (AS)**. An AS is a network under one administrative control with one routing policy, such as an ISP, a university or a hosting provider.

Each AS has a unique number, the **ASN**:

- 16-bit ASNs: `1`–`65535`.
- 32-bit ASNs: up to `4294967295`, written as plain numbers, for example `AS4200000000`.
- Private ASNs: `64512`–`65534` and `4200000000`–`4294967294`. Use them inside your own network, like private IP ranges.

Public ASNs and IP address space are assigned by the **Regional Internet Registries (RIRs)**: ARIN, RIPE NCC, APNIC, LACNIC and AFRINIC.

An AS announces the IP prefixes it owns. Other ASes learn those announcements and pass them along. That is the whole internet routing table: a list of prefixes and the AS paths to reach them.

# eBGP and iBGP

BGP has two modes:

- **eBGP** (external BGP) runs between different ASes. This is how networks exchange routes with each other.
- **iBGP** (internal BGP) runs between routers inside the same AS. It distributes externally learned routes across your own network.

The rules differ. A route learned over iBGP is not re-advertised to other iBGP peers by default, so iBGP needs a full mesh or **route reflectors**. eBGP prepends the local ASN to the path; iBGP does not.

# How a BGP session works

BGP runs over **TCP port 179**. Two routers configured as neighbors (**peers**) open a TCP connection and move through these states:

1. **Idle** — not trying yet.
2. **Connect / Active** — opening the TCP connection.
3. **OpenSent / OpenConfirm** — exchanging `OPEN` messages with ASN, router ID, hold time and capabilities.
4. **Established** — the session is up and routes flow.

Four message types do all the work:

| Message | Purpose |
|---|---|
| `OPEN` | Starts the session and negotiates capabilities. |
| `UPDATE` | Announces new routes or withdraws old ones. |
| `KEEPALIVE` | Confirms the peer is still alive. |
| `NOTIFICATION` | Reports an error and closes the session. |

After the initial exchange, BGP only sends changes. It does not resend the full table periodically.

# Path attributes

Every route carries **path attributes**. These are what BGP uses to choose between routes and to express policy.

- **AS_PATH** — the list of ASes the route has passed through, for example `64500 64501 64502`. It is used for loop prevention: a router rejects a route containing its own ASN. Shorter paths are generally preferred.
- **NEXT_HOP** — the IP address to forward traffic to for this prefix.
- **LOCAL_PREF** — preference inside your own AS. Higher wins. Used to pick an exit point.
- **MED** (Multi-Exit Discriminator) — a hint to a neighbor AS about which of your links it should use to enter. Lower wins.
- **ORIGIN** — how the route entered BGP: `IGP`, `EGP` or `incomplete`.
- **Communities** — tags attached to routes, such as `64500:100`. Peers use them to signal actions like "do not export" or "prepend to this region". Large communities ([RFC 8092](https://www.rfc-editor.org/rfc/rfc8092)) extend this to 32-bit ASNs.

# How BGP picks the best path

When a router has several routes to the same prefix, it compares them in order and stops at the first difference. A simplified version of the decision process:

1. Highest **LOCAL_PREF**.
2. Shortest **AS_PATH**.
3. Lowest **ORIGIN** (`IGP` < `EGP` < `incomplete`).
4. Lowest **MED** (when from the same neighbor AS).
5. eBGP over iBGP.
6. Lowest IGP cost to the next hop.
7. Lowest router ID as a final tie-breaker.

Vendors add their own steps (Cisco's *weight*, for example), but the shape is the same everywhere.

The key point: BGP is not about the fastest path. It is about **policy**. LOCAL_PREF comes before AS_PATH, so business decisions override path length.

# Policy: why BGP is about relationships

Networks connect under two common arrangements:

- **Transit** — you pay a provider to carry your traffic to the whole internet. They announce your prefixes to everyone and give you a full table or a default route.
- **Peering** — two networks exchange traffic for each other's customers, usually free. Peering often happens at an **Internet Exchange Point (IXP)**, where many networks connect to a shared switch, often through a route server.

From these relationships comes the standard export rule:

- Send **customer routes** to everyone.
- Send **peer and provider routes** only to customers.

Breaking this rule turns you into free transit for other networks. That is a **route leak**.

# Security: the weak spot

BGP was designed on trust. By default, a router accepts any prefix its peer announces. This causes two common problems:

- **Hijacks** — an AS announces a prefix it does not own, by mistake or on purpose, and pulls traffic toward itself.
- **Leaks** — an AS re-announces routes it should have kept to itself, breaking the export rule above.

The main defenses:

- **IRR filtering** — build prefix filters from Internet Routing Registry objects (`route`, `route6`, `as-set`). Tools like `bgpq4` generate them.
- **RPKI** — the prefix owner signs a **ROA** (Route Origin Authorization) stating which ASN may originate the prefix and the maximum prefix length. Routers validate each route as `valid`, `invalid` or `not-found` and drop `invalid`.
- **Max-prefix limits** — tear down a session if a peer suddenly sends far more prefixes than expected.
- **Bogon filtering** — reject private, reserved and unallocated ranges and private ASNs from the internet.
- **[MANRS](https://manrs.org/)** — a community baseline that bundles these practices.

Filter what you accept and filter what you send. Never run a public BGP session without both.

# A minimal example

Here is a small BIRD 2 configuration that announces one IPv6 prefix to an upstream. It uses documentation ASNs and addresses.

```
router id 192.0.2.1;

define OUR_ASN = 64500;
define OUR_PREFIXES = [ 2001:db8:1000::/48 ];

protocol device {}

protocol static announce_v6 {
    ipv6;
    route 2001:db8:1000::/48 unreachable;
}

filter export_upstream {
    if net ~ OUR_PREFIXES then accept;
    reject;
}

filter import_upstream {
    if net.len > 48 then reject;
    if roa_check(roa_v6, net, bgp_path.last) = ROA_INVALID then reject;
    accept;
}

protocol bgp upstream {
    local 2001:db8:ffff::2 as OUR_ASN;
    neighbor 2001:db8:ffff::1 as 64501;
    ipv6 {
        import filter import_upstream;
        export filter export_upstream;
        import limit 250000 action restart;
    };
}
```

What it does:

- The `static` protocol creates the `/48` locally so BGP has something to announce.
- The export filter announces only your own prefix.
- The import filter rejects prefixes longer than `/48` and RPKI-invalid routes. The `roa_v6` table needs an RPKI source, such as an RTR session to a validator like Routinator or rpki-client.
- The import limit restarts the session if the peer sends too many routes.

# How to get started

You can run BGP on the real internet as an individual. The usual path:

1. **Learn in a lab.** Run BIRD or FRRouting in containers or VMs and peer them with private ASNs. Try [DN42](https://dn42.dev/), a hobby network that uses real BGP, registries and ROAs without real-world risk.
2. **Get an ASN and IP space.** Apply through an RIR directly, or through a **LIR / sponsoring organization** that handles the paperwork. For example, JianyueLab can [sponsor your ASN through RIPE NCC](https://jianyuelab.co/services/asn/) and assign [PI or PA IPv6 space](https://jianyuelab.co/services/ipv6/). IPv6 `/48` blocks are inexpensive. IPv4 is scarce and costly.
3. **Create registry objects.** Register `aut-num`, `route6`/`route` and an `as-set` in an IRR, and sign ROAs in RPKI.
4. **Find a BGP-capable host.** Several VPS providers offer BGP sessions. Some will give you a full table, or you can buy [IP transit](https://jianyuelab.co/services/ip-transit/) directly.
5. **Peer at an IXP.** Once comfortable, join an exchange and peer with its route servers.

# Summary

- The internet is a network of Autonomous Systems, each with an ASN.
- BGP is how those ASes tell each other which prefixes they can reach.
- It runs over TCP 179 and sends only changes.
- Route selection is driven by attributes, and policy comes before path length.
- BGP trusts by default, so filtering, IRR and RPKI are mandatory.
- You can start in a lab or on DN42 before announcing real prefixes.
